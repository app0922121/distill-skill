# 05 · 规则库与 skill 草稿（第二层产出）

用户要「把方法提炼出来给 AI 用」「做成规则库」「做成 skill」时读这份。前提是精华解析已经做完并通过核对。

## 1 什么能进规则库

规则库只收**能指导下一步怎么做**的内容：步骤、判据、阈值、决策规则、检查清单、常见错误。定义、背景、故事不进（它们留在精华解析里）。

材料等级的限制：

- T1：正常出。
- T2：只能出「草稿·未核原文」，文件开头写明，每条挂网页来源的锚。
- T3：不出。告诉用户需要原文。

不是每本书都适合。论述、叙事、历史类的书往往没有多少可执行的规则，硬提会编出作者没有的方法。底稿里「方法步骤」「判据与阈值」类条目很少时，如实告诉用户这本书不适合做规则库，可以改做「核心观点速查」。

## 2 规则条目格式

写进 `W/rulebook.md`，从底稿（`notes/`）取材，不从成稿取材：

```markdown
## R07 · 先诊断再给方案
- **什么时候用**：对方已经承认有问题，但还没说清问题有多大。
- **怎么做**：
  1. 先问开放式问题，让对方自己描述现状〔p45〕
  2. 再问控制式问题，把范围和数字问出来〔p46〕
  3. 最后复述确认〔p47〕
- **做到什么算数**：对方能用自己的话说出问题的代价〔p48〕
- **什么时候不要用**：对方已经带着明确的规格书来询价〔p52〕
- **常见错误**：对方还没承认问题就开始介绍产品〔p44〕
- **依据强度**：书内有完整步骤和两个案例
```

要求：

- 每一行都挂锚。挂不上锚的内容不进规则库。
- 步骤、数字、顺序照原书。原书没写「什么时候不要用」的，这一行写「原书未说明」，不要自己补。
- 「依据强度」如实写：有完整步骤和案例／只有原则没有步骤／作者只提了一句。每条都要写，不只给拿得出手的写。
- 整理者自己的使用建议放在条目末尾的 `> [评注]` 块里。
- 写完跑 `python3 S/verify.py quotes W`，`rulebook.md` 会一起查。

**先自己过一遍**：拿书里的一个案例，只看规则条目，能不能一步步走到书里的结果？走不通，说明抽漏了步骤或前提，回底稿补。

## 3 要做成 skill 时

默认**一本书一个 skill**：一份简短的 `SKILL.md` 当入口，规则条目放进 `references/`。不要每条规则拆一个 skill——拆多了互相抢触发，装起来也是负担。只有当某条方法足够独立、会被单独反复调用、而且和书里其他内容用的场合不同，才单拆。

草稿放在 `W/skill-draft/<名字>/`，不直接装进用户的 skill 目录：

- `SKILL.md`：说明这个 skill 帮人做什么事；列出有哪些规则、各自在什么情况下读哪个文件；写明来源（书名、作者、版本）和材料等级。
- `description` 的写法：做什么事＋用户会怎么说＋书里独有的概念词；再写两句不触发的情况——用户只是想要这本书的摘要时不触发；一般性的领域问题、没有提到这本书的方法时不触发。
- `references/`：规则条目，按使用场合分文件；每个文件在 `SKILL.md` 里写明何时读。
- 保留锚。使用者要能回到原书核对。

交给用户时说明四件事：

1. 这是草稿，没有做过触发测试和效果对比；要正式用，建议走一遍 skill 评测（有无 skill 各跑一遍真实任务）。
2. 安装需要用户自己决定，装到哪里、叫什么名字。
3. skill 里的规则来自一本书，是作者的方法，不等于在用户的场合一定有效。
4. 在版书提炼出的 skill 留在本机自用；要公开分享，先确认版权上是否合适，并去掉大段原文引语。
