# 05 · 把书做成 skill

用户选了「做成 skill」或「两样都要」时读这份。这里是完整做法，不依赖别的 skill。

前提：第 0–3 步已经做完（材料登记、地图、底稿、底稿核对通过）。做 skill 从**底稿**取材，不从精华解析取材；用户只要 skill、不要摘要时，第 4–6 步可以不做，`references/03-digest.md` 不用读，`references/04-verify.md` 只读第 1 节（机器核对）和第 2 节的任务书写法。

只做 skill 时，抽底稿的重心放在方法、判据、清单与名目、反例与边界上；背景、定义、故事、长长的症状清单，底稿里每处记一行（是什么、在哪页）就够，不必逐条抄。

## 1 先看这本书适不适合

skill 是给 AI 用的操作手册，只收**能指导下一步怎么做**的内容：步骤、判据、阈值、决策规则、检查清单、常见错误。定义、背景、故事不进。

- 数一下底稿里「方法步骤」「判据与阈值」「清单与名目」「反例与边界」这几类条目。很少（不到五六条）时，如实告诉用户这本书多半是观点或叙事，硬做会编出作者没有的方法，建议只出摘要。
- 材料等级：T1 正常做。T2 只能做「草稿·未核原文」，在 skill 开头写明，每条规则挂网页来源的锚。T3 不做，告诉用户需要原文。

## 2 定这个 skill 帮人做什么事

写三句话，写不出来就先别往下做：

1. **任务**：装了这个 skill 的人，会拿它做哪一件具体的事？（「用某书的方法诊断一个销售机会卡在哪」，不是「了解某书」。）
2. **用户原话**：他会怎么开口？写三五句真人会说的话。
3. **需要用户提供什么**：做这件事要先知道哪些情况。

一本书默认只做**一个** skill。书里有两三件互不相干的事（比如既讲怎么写、又讲怎么谈判），也先做成一个 skill 里的两三组规则；只有某一组会被单独反复调用、用的场合和别的完全不同，才单拆。拆多了互相抢触发，装起来也是负担。

## 3 先列方法清单，再决定收什么

动手写规则前，把材料里**所有可以照着做的东西**列成一张表，存 `W/verify/skill-inventory.md`：

| # | 方法、判据或步骤 | 出处 | 收不收 | 理由 |
|---|---|---|---|---|
| 1 | 按需求三个层次判断买方 | p39-41 | 收 → R03 | |
| 2 | 用价值分析、ROI 证明方案值得 | p53 | 收 → R11 | |
| 3 | 64% 难题 | p31 | 不收 | 是背景，没有做法 |

- 判断标准只有一个：**使用者照着它能不能做出一个动作或一个判断**。能，就收；只是背景、定义、故事、统计，就不收（它们留在摘要里）。
- 作者一笔带过的工具（只提了名字、说了用途、没讲做法）也收，规则里写清「本材料只给了名字和用途，做法在原书别处」，免得 AI 以为没有这回事。
- 宁可多收几条短规则，也别为了精简把能照做的方法丢掉。这张表也是之后核对覆盖的依据。

## 4 把清单变成规则

**一条规则对应一个使用者会单独遇到的情况**（「判断客户在哪个阶段」「对方说先报个价」），里面是这个情况下要做的一串动作。别把一个动作拆成一条规则，也别把整章塞进一条。

每条规则一个条目，写进 `W/skill-draft/<名字>/references/` 下的文件里：

```markdown
## R07 · 先诊断再给方案
- **什么时候用**：对方已经承认有问题，但还没说清问题有多大〔p45〕
- **怎么做**：
  1. 先问开放式问题，让对方自己描述现状〔p45〕
  2. 再问控制式问题，把范围和数字问出来〔p46〕
  3. 最后复述确认〔p47〕
- **做到什么算数**：对方能用自己的话说出问题的代价〔p48〕
- **常见错误**：对方还没承认问题就开始介绍产品〔p44〕
- **依据强度**：书内有完整步骤和两个案例
```

「什么时候用」「怎么做」「依据强度」三栏必有。「做到什么算数」「什么时候不要用」「常见错误」三栏**原书有才写，没有就整行省掉**，不要写一排「原书未说明」。

- 每一行都挂锚。挂不上锚的内容不进规则。
- 步骤、数字、顺序、限定词（「很可能」「通常」）照原书，不要把「很可能」写成「默认」。「什么时候用」和「怎么做」必须有原书依据，写不出来说明这条不该成为规则。
- **你自己定的标准、排序、推论**（「下一步落在最早出现缺口的地方」「对方往上走了一层就算推进」）不能挂原书页码冒充作者的话。确实有用的，单独写一行，以「整理者补充：」开头，不挂锚。
- 「依据强度」如实写，一句话说清依据有多足：比如「有完整步骤和案例」「只有原则没有步骤」「作者只提了一句」「作者明确主张，但没给做法」。每条都写。
- 你自己的使用建议放在条目末尾的 `> [评注]` 块里。
- 规则多于七八条时，按**使用场合**分成几个文件（如 `diagnose.md`、`close.md`），不按书的章节分。

## 5 组装 skill 包

```
W/skill-draft/<名字>/
├── SKILL.md            入口，尽量短
└── references/         规则条目，按使用场合分文件
```

`<名字>` 用小写英文加连字符（如 `solution-selling-diagnose`），和 `SKILL.md` 里的 `name` 一致。

`SKILL.md` 照这个样子写：

```markdown
---
name: <名字>
description: <做什么事>。<用户会怎么说：三五个说法>。<书里独有的概念词>。不用于：只想要这本书的摘要；没有提到这本书的方法的一般性问题。
---

# <标题>

用《书名》（作者，版本）里的方法帮你做 <什么事>。这些规则是从原书全文整理的，每条带页码，可以回原书核对。（只读到部分材料时照实写：「据目录和试读章节整理，未核原文」。）

## 先问清楚
开始前需要用户提供的情况，没给就先问：……

## 怎么做
1. 根据用户的情况判断适用哪组规则（见下表）
2. 读对应的文件，按规则里的步骤一步步做。书里的方法要求逐个判断的对象（每一个相关的人、每一个阶段、每一项条件），逐个判断，不要笼统给一个结论
3. 按下面的输出格式回答，每个判断写明用的是哪条规则（R 编号和出处页码）
4. 规则没覆盖到的情况，直说「这本书没有讲到」，不要自己编，也不要拿常识冒充书里的方法

## 输出格式
（一个固定的骨架，让每次回答结构一致。例如：先问清的情况 → 逐项判断，每项一行：对象｜判断｜依据规则 → 建议的下一步，每步写清用哪条规则、做到什么算数 → 这本书没讲到、需要用户自己判断的地方）

## 示例
（拿书里的一个案例，按上面的输出格式完整走一遍，十几行即可。示例里的判断都要能在规则文件里找到出处。）

## 规则在哪
| 情况 | 读哪个文件 |
|---|---|
| 要判断客户处在哪个阶段 | `references/diagnose.md` |

## 底线
- 这些规则是作者的方法，不保证在每个场合都有效；用之前先核对「什么时候不要用」。
- 只用规则文件里写了的内容，不凭对这本书的印象补充。

```

装上以后用的时候发现反复犯的错，再在末尾加一节「踩坑点」；一开始不必留空节。

写法上的硬约束（脚本会查）：

- `description` 是决定这个 skill 会不会被调用的唯一依据。写成「做什么事＋用户会怎么说」，不用「我」「你」，两百字以内。再写两种**不触发**的情况，免得它抢别的 skill 的活。
- `SKILL.md` 正文不超过两百行，要有「输出格式」和「示例」两节。规则的细节全放 `references/`。
- `references/` 里每个文件都要在 `SKILL.md` 里写明**什么情况下读它**；没被提到的文件等于不存在。
- 引用只一层：`SKILL.md` 指向 `references/` 里的文件，那些文件不再指向别的文件。
- 保留锚，使用者要能回到原书核对。
- 规则文件里的原话一样要逐字：引号里十二个字以上的内容脚本会去原文里找。

## 6 检查

```bash
python3 S/verify.py skill W          # 查 skill 包的结构、每条规则有没有锚、锚和引文对不对
```

问题清零后做三件事，结果都存进 `W/verify/`：

1. **纸面走一遍**（存 `skill-walkthrough.md`）：拿书里的一个案例，只看 skill 包，按 `SKILL.md` 的流程一步步走，看能不能走到书里的结果。走不通，多半是漏了步骤或前提，回底稿补。
2. **规则核对**（存 `skill-check.md`，能派子代理就做）：规则是要被 AI 当指令执行的，转述走样的代价比摘要大。派一个没参与写作的核对者，只给它 skill 包和原文，照 `references/04-verify.md` 第 2 节的任务书逐条核：每条规则是不是原文的意思，有没有原文没有的步骤或判断挂着原书页码，限定词有没有丢或被说满。再请它通读原文，列出所有可以照着做的方法，看 skill 里漏了哪些。处理办法同第 2 节；漏掉的能照做的方法补成规则。
3. **试用一次**（能派子代理就做）：
   - 任务：用户给过实际问题就用它；没有就把书里的一个案例改掉人名、行业和细节，变成一个新问题；书里没有案例时，写一个这个领域里常见的、需要用到书中方法的问题。
   - 派两个子代理做同一个任务：一个只给 skill 包，一个什么都不给。都要求先把回答写进文件（`skill-trial-with.md`、`skill-trial-without.md`）再回报，免得中途断掉回答丢了。
   - 对比（存 `skill-trial.md`）只看三件事：带 skill 的那份有没有用上书里的具体步骤和判据；有没有说出规则里没有、却当成书里方法的东西；比不带 skill 的那份多给了什么、少给了什么。差别不大，说明规则写得太空，回去把步骤和判据写具体。
   - 你自己出题、自己写 skill、自己判，对比不算独立，交付时照实说。

## 7 交付

- skill 包留在 `W/skill-draft/<名字>/`，**不自动安装**。告诉用户：想用就把这个文件夹复制到自己的 skill 目录（Claude Code 是 `~/.claude/skills/`）。
- 汇报里说清：收了多少条规则、分了几个文件；哪些内容因为没有可执行的步骤而没收；机器检查的结果；规则核对查了多少条、改了几条；有没有做试用对比、结果如何；材料等级。
- 书里有张关键的图表只剩零散文字、因而没能变成规则时，告诉用户：拍一张那一页的照片或截图给你，可以补进去。
- 提醒两点：这是从一本书提炼的方法，不等于在用户的场合一定有效；在版书提炼出的 skill 适合自己用，要公开分享先确认版权上是否合适，并去掉大段原文引语。

## 只要规则清单、不要 skill

用户说「只要把方法列出来」「做个规则库」时：只做第 1、3、4 步，规则条目写进 `W/rulebook.md`，跑 `python3 S/verify.py quotes W` 核对。
